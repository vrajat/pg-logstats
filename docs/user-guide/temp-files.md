# `pg-logstats temp-files`

`pg-logstats temp-files` triages temp-file-driven resource pressure inside a bounded historical log window.

## Supported Mode

This workflow supports `log_backed` mode only.

At startup, `pg-logstats` requires a persisted `inspect` report. This workflow then requires that the stored inspect report says `operating_mode` is either `log_backed` or `log_backed_and_live`.

If the inspect report is missing, startup fails and points you to `pg-logstats inspect`.

The inspect artifact is read from the workspace directory:
- default workspace: `~/.local/share/pg-logstats`
- override with `--workspace <dir>` or `PG_LOGSTATS_WORKSPACE`
- inspect artifact path: `<workspace>/inspect.json`

## Bounded Historical Window

The command parses temp file events over the specific log window you provide:
- one or more local PostgreSQL log files
- `--log-dir` discovery
- AWS RDS / CloudWatch windows when using the RDS input path

The report includes standard historical metadata:
- `analysis_window.since`
- `analysis_window.until`
- `source_summary.kind`
- `source_summary.scanned_entries`

## Required Log Evidence & Parsing

The parser identifies temporary file creation logs generated by PostgreSQL:
- **Prerequisites**: PostgreSQL must be configured to log temp files (e.g., `log_temp_files = 0` or higher). Use `pg-logstats inspect` to verify this config check.
- **Parsing**: Automatically parses log entries containing `LOG:  temporary file: path "...", size ... bytes`.
- **Nearby Statement Correlation**: Since temporary file creation events in PostgreSQL logs usually *do not* contain the query SQL text on the same line, the tool matches the database process ID (PID) of the temp file event and searches backward and forward in the logs to locate the closest executed query statement from the same PID. This provides direct attribution of temp file size pressure to query families.

## Attribution & Output Format

Each finding outputs the following fields when available:
- `query_family_id`: The ID of the query family correlated with the temp file event.
- `normalized_sql`: The query text correlated with the temp file creation.
- `database`: Database where the temp file was created.
- `user`: User executing the query.
- `application_name`: Application name from connection properties.
- `largest_observed_bytes`: Size in bytes of the largest temp file observed for this query family.
- `temp_file_count`: Number of temp file events attributed to this query family.
- `total_bytes`: Sum of bytes of all temp files created by this query family.

Example finding payload:
```json
{
  "id": "qf_c05e64f15dea15ce",
  "kind": "temp_file",
  "rank": 1,
  "title": "Temp file creation for SELECT * FROM giant_table ORDER BY name",
  "reason": "Created 5 temp files (total 25.0MB; largest 5.0MB)",
  "score": 25000000.0,
  "confidence": "high",
  "temp_file": {
    "query_family_id": "qf_c05e64f15dea15ce",
    "normalized_sql": "SELECT * FROM giant_table ORDER BY name",
    "database": "appdb",
    "user": "app",
    "application_name": "api",
    "largest_observed_bytes": 5000000,
    "temp_file_count": 5,
    "total_bytes": 25000000
  }
}
```

## Diagnostic Next Actions

If the triage report connects to a database in `log_backed_and_live` mode, it emits next actions to run follow-up diagnostic SQL queries:
- `temp_file.pg_stat_database.temp_counters`: Returns the total count and bytes of temporary files created in the specified database using `pg_stat_database`.
- `temp_file.pg_stat_statements.temp_blocks`: Emits a query querying `pg_stat_statements` for queries that have accumulated the highest `temp_blks_read` or `temp_blks_written` counters.
